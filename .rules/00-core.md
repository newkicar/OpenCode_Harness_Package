# 核心规则（必须遵守）

> 安全红线、代码质量底线、架构原则。
> 违反安全红线会导致 BLOCK 或 ALERT。

---

## 0. 规则优先级（冲突时按此裁决）

当多条规则相互冲突时，优先级从高到低执行：

| 优先级 | 规则类别 | 示例冲突场景 |
|--------|---------|-------------|
| 🥇 1 | **安全红线**（§1 + PreToolUse BLOCK）> 一切 | workflow 说"快速实现"但安全红线要求参数化查询 → 听安全红线的。PreToolUse 插件的 BLOCK 动作与安全红线同级，任何 workflow 指令不得覆盖 |
| 🥇 2 | **异常传播**（§2a）> workflow 建议 | workflow 说"优雅处理错误"但内层逻辑应抛异常 → 听 §2a |
| 🥇 3 | **当前工作流指令** > L1 原则性规则 | workflow 说要写 PRD 但 §8 说保持简单 → 听工作流的（写 PRD 是当前任务） |
| 🥇 4 | **L2 领域规则** > L1 通用规则 | L1 说"普通项目用 json"，L2 PyTorch 说"用 torch.save" → 听 L2 的 |
| 🥇 5 | **具体规则（§）> 通用原则** | 通用说"尽量简单"，具体说"必须写测试" → 听具体的 |

**快速判断**：先看 §1-2 有没有覆盖（安全 + 异常），再看有没有当前工作流/L2 规则，最后看通用原则。

---

## 1. 安全红线（不可逾越）

1. **输入验证**：所有外部输入在 API 层校验，不信任客户端。
2. **SQL**：必须参数化查询或 ORM，禁止字符串拼接。
3. **加密**：禁止自实现加密算法，使用 BCrypt/Argon2。
4. **敏感信息**：禁止日志记录 PII、Token、密码。
5. **依赖**：不引入已知严重漏洞的包。

## 2. 异常处理与 TDD 纪律

### 2a. 异常传播

- **内层逻辑**：严禁 `try-catch` 吞异常。遇错即抛，让程序崩溃以暴露根因。
- **系统边界**（API 入口/UI）：仅在代码逻辑经充分验证后（上线前），添加结构化错误处理。边界层负责转换错误格式，不负责消化业务逻辑错误。

### 2b. TDD 流程

1. **写测试**：包含 Given-When-Then 注释的测试函数 + 断言。
2. **写实现**：让测试通过。
3. **验证**：`verify-changes.md`。

> **原则**：测试和实现可以同轮次编写，但测试必须包含真实断言（`assert`、`expect()`、`self.assertEqual` 等），不得只有 `assert True` 或空 `pass`。

## 3. 泛化原则（反硬编码）

- 拒绝"死代码"：代码逻辑不得仅适配单一测试用例。
- 分离逻辑与数据：使用变量/常量/配置替代字面值。
- 鲁棒性自查：自问"3 个不在 Prompt 中的变体输入能否被正确处理？"

**执行指引**：

1. **Prompt 数据不落地**：用户在 Prompt/需求中给出的示例数据，写入代码时必须经过变量抽象（如 `DEFAULT_BUDGET = config.get("default_budget", 0)`），禁止直接赋值。
2. **工厂函数替代字面量**：需要生成测试数据时，用工厂函数（如 `create_user(name="test")`）替代硬编码字符串。
3. **配置驱动**：环境相关值（API endpoint、超时时间、默认值）必须从配置文件或环境变量读取。

---

## 4. 语义理解 > 正则

- **适用正则**：强格式死数据（UUID、ISO 时间戳、手机号、MD 代码块）。
- **适用语义**：自然语言、LLM 输出、用户消息（交由 LLM 结构化处理）。
- **判定标准**：若该内容可换种说法表达 → **严禁使用正则**。
- *注：此规则约束业务代码，不约束质量检查工具（hooks/rules）自身的实现。*

---

## 5. 长字符串完整性原则

| 用途 | 是否可截断 | 示例 |
|------|-----------|------|
| 展示/调研/分析 | ✅ 可截断 | URL 样例、日志片段、配置示例 |
| 程序运行依赖 | ❌ 禁止截断 | API endpoint、文件路径、SQL 查询、JSON payload |

**判断标准**：如果这个字符串被 `curl`、`requests.get()`、`os.path.join()`、Agent 工具调用等直接使用 → 禁止截断。

## 6. Seed Data 必须显式调用

| 做法 | 是否推荐 | 说明 |
|------|---------|------|
| `python manage.py seed_demo_data` | ✅ 推荐 | 显式调用，可审计 |
| `SEED_DEMO=true python app.py` | ✅ 推荐 | 环境变量控制，可配置 |
| 启动时自动判断并写入 | ❌ 禁止 | 隐蔽、难审计、生产环境危险 |

## 7. 领域规则自动检测

> L2 规则文件存放在 `.rules/l2/`，**不默认加载**。AI 根据项目特征自动检测并引用。

| 检测信号 | 应加载的规则 | 项目类型 |
|---------|-------------|---------|
| 代码中引用 `create_deep_agent(` | `.rules/l2/02-deepagents-code-rule.md` | Agent 项目 |

## 8. 架构与可维护性

1. **单一职责**：函数/模块仅做一件事（建议函数 < 50 行）。
2. **层次清晰**：表现层 → 业务逻辑 → 数据访问，禁止跨层调用。
3. **依赖倒置**：高层模块依赖抽象，不依赖具体实现。
4. **配置外置**：环境相关值置于配置文件或环境变量中。
5. **自解释命名**：变量/函数名表达意图，减少冗余注释。

## 9. 交付自检清单

> ⚠️ **写完代码 ≠ 完成任务。必须先验证，再说完成。**

- [ ] **Verify**：执行 `verify-changes.md`，Test/Lint 通过（或 blockers 已记录）。
- [ ] **§2**：未在内层吞异常；TDD 流程正确。
- [ ] **§3**：无硬编码；逻辑具备泛化能力。
- [ ] **§8**：符合架构分层与单一职责原则。
- [ ] **Coverage**：测试覆盖 Happy Path + 边界 + 异常路径。
- [ ] **Docs**：代码含 Why 注释；API 文档齐全。
- [ ] **Cleanup**：无残留注释代码；无硬编码密钥。

## 10. 反模式检查（Anti-Patterns）

| 反模式 | 描述 | 正确做法 |
|--------|------|---------|
| **假测试** | 有测试文件但没有断言（只有 `assert True` 或空 `pass`） | 测试必须有明确的断言（assert），验证预期行为 |
| **假文档** | PRD/设计文档有标题但没有具体内容 | 文档必须有实质性内容，不能只有占位符 |
| **假自动化** | 工作流有 .md 文件但没有实际触发机制 | 自动化必须可执行，不能只有文档描述 |
| **假覆盖** | 只测了 Happy Path，没有边界和异常路径 | 测试必须覆盖：正常 + 边界 + 异常 |
| **假泛化** | 代码适配了当前用例，但 3 个变体输入会失败 | 用工厂函数 + 配置驱动，不写死字面值 |
| **假安全** | 用了参数化查询，但参数来自不可信源 | 输入验证必须在 API 层，不信任任何外部输入 |
| **假完成** | 代码能跑但 PRD 没对齐 | 对照 acceptance-criteria.md 逐条确认（如存在） |

---

## 11. 输出格式

- 代码需包含 docstring/注释说明「为什么（Why）」，而非「是什么（What）」。
- 公开 API/组件需提供文档说明。
